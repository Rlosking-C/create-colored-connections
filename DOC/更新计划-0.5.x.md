#### P1-2　修复有状态连线在拐角处的渲染（截图一）

- **目标**：活动状态连线（状态色核心 + 染料描边）在 L 形转角处描边连续，无台阶、错位与内侧方形叠色
- **现状依据**：描边是**逐段**实现的——`FactoryPanelRendererMixin.createcc$underlay(...)` 对每一段线段用 `widthScale = 2`（沿宽度轴放大）画出每侧 1px 的染料描边，段与段之间没有任何转角联合处理；首段还叠两层（`FACTORY_PANEL_LINES` 2× 与 `FACTORY_PANEL_ARROWS` 1.5×）来对齐箭头宽度；活动线额外有 `yOffset -0.0625` 的层级偏移，用来避免核心穿透水平线的描边
- **参考 Create 本体（已核对源码）**：Create 的连线模型只有 `line_{east,west,north,south}`、`dotted_*`、`arrow_*` 共 12 个文件，元素尺寸是 **0.5 格长 × 0.25 格宽**（见 `models/block/factory_gauge/connections/line_east.json`），**没有任何转角模型**——上游的转角就是两段直角相接。
      结论：转角缺口不是"上游漏做"，而是**我们把整段描边放大 2× 叠加**造成的；这块没有可直接照搬的上游范式，转角形状需要自定（这也是为什么必须先定"斜接 vs 补角方块"）。
- **建议实现**（先定形状再动代码，二选一）：
      a) **补角方块**：在转角处补一块与描边同宽的方块几何，转角形状为直角块
      b) **端点重叠**：相邻两段的描边各自在端点延长半个线宽做重叠，并把层级偏移按段统一，避免水平/垂直段在转角互相穿插
- **验收**：4 种转角方向 × 闲置 / 进行中 / 已满足 / 失败 四种状态逐张截图核对；转角处描边宽度恒为 1px，无叠色块、无断口
- **实现结果（已完成，0.5.0-dev）**：形状定为**补角方块**（方案 a），并顺带消除了内侧叠色——两个问题同源。
      做法与预览光束完全一致，只是作用在描边的"带宽"上：描边的可见带宽为 `2 × widthScale` px（非闲置=4px、闲置=2px），所以
      1. **裁掉重叠**：跨接点的那一段把自身起点裁掉"半个带宽"（4px 带 → 裁 2px），用的是模型自带的长度缩放——模型四边形正好是从段起点向锚点方向覆盖，缩放裁的正是段起点这一端，天然对上；
      2. **补外侧象限**：在接点处补一块"半带宽长 × 整带宽宽"的同色片段，方向沿用**来向**那一段（锚点向来向多偏半个带宽），恰好填满两段直角相接时外侧留出的象限，且与两段**相接而不重叠**。
      闲置档（整条线直接显示染料色、带宽 2px）同样处理，只是裁 1px、补 1px×2px。
      防护：路径首尾各有一个"面朝面板"的零位移步进（`planar()` 判定），它不构成转角，跳过补角，否则会在仪表内部落下一小块色带。
- **第二轮修正（作者反馈"你反而覆盖了原版核心"）**：根因是**层**。本体给两条轴设了 0.125/512 的层差（E-W 与 N-S 不同层），而描边只比自己那段核心低 0.0625：
      1. 补角块沿用来向那一段的层，若来向层的数值更高，补角块就会压在**另一段的核心之上**，把原版连线涂成染料色；
      2. 同理，**来向那条 4px 宽带**本身也会盖住另一段核心的首 2px——这不是补角块引入的，是原设计与层差共同造成的。
      改法：**两段各自在转角处收进半个带宽**（4px 带 → 各收 2px；闲置 2px 带 → 各收 1px），补角块扩成 `2w × 2w` 的方块（非闲置 4px×4px），并且**取两段中较低的那一层**，保证它永远在两段核心之下。收掉之后，两段核心都不再被染料覆盖，缺口由补角块补齐。
      实现细节：模型自带的长度缩放只能裁"段起点"那一端，所以要裁的**远端**用"同样按起点裁 + 锚点沿行进方向回退半个带宽"表达（`shiftedX/shiftedZ`）；转角判定用带前瞻的 `isCorner(prev, next)`。
- **第三轮调整（作者定稿形状）**：先按作者要求整体关掉补角块看效果（`CORNER_FILL = false`），确认转角会露出缺口；随后作者逐张指出缺口位置，最终形状为**把两段各自被裁掉的那一格补回来**：
      实现：补角块由"一块"改为**每段各补一块**（都取两段中较低的那一层，保证压不到任何核心）——
      1. **来向那块**：沿来向 1 个带宽长、止于转角，横向偏向来向线的**外侧**半格（补它被裁掉的那一格）；
      2. **去向那块**：沿去向 1 个带宽长、起于转角，横跨去向线的整个带宽（补它的裁掉部分，含内外两侧的描边格）。
      结果：两条臂的描边在转角处都接上；**只剩肘部对角外侧的那一格是空的**（作者要的留空，也让转角不会糊成一整块方块）。
      `CORNER_FILL` 开关仍在，便于以后一键对比。形状已通过，作者认为描边颜色"还可以改善（更自然、更贴合 Create）"，但选择先不动。
      已查清的根因（改的时候不用再查一遍）：本体连线贴图 `create:textures/block/factory_panel_connections.png`（16×16）里，每段线只有 **2px**——一列亮 `0xD2/0xC8`、一列暗 `0x8C/0x82`，即线条自带"一亮一暗"的斜面质感。描边是把同一模型按宽度放大后乘染料色，于是**暗的那一半把染料色压暗**（黄 → 暗金/黄铜），看起来像给核心镶了一圈金属边。
      三个候选方案（代价递增）：
      a) **提亮染料色**：一行改动，让暗半落到接近染料本色；代价是亮半会被推到接近白色，明暗层次仍在
      b) **纯色实心描边**：改用与路径预览光束同一套实心渲染（不贴图），绝对干净；代价是描边失去随线流动的纹理动画
      c) **自带贴图接管描边**（最贴合且最干净）：复制本体那张 16×16 贴图、把线段的两个像素列改成同一亮度，配 4 个沿用本体几何的模型 JSON，描边走自己的贴图——UV 与流动动画都与本体一致，颜色却是均匀的染料色
      建议将来若要动手，从 c 开始（观感最好、与本体同源，动画不丢）。
- **第四轮定稿（作者反馈"描边贴图花纹太密"）**：根因是**裁切本身**——`SuperByteBuffer.scale(...)` 只是给顶点乘矩阵（已反编译 `DefaultSuperByteBuffer.scale(FFF)` 确认，它就是 `transforms.scale(x,y,z)`，**不碰 UV**），所以"把 8 格的模型压到 2 格"等于把贴图里 **8 个像素**的花纹硬挤进 2px，密度变成 4 倍；被裁两端的正常段也各有约 1.33 倍。补角块只有 4px×2px 大，却带着 4 倍密的花纹，正是"密"的来源。
      定稿做法：**彻底不裁切、不补角**，转角靠层来解决——
      1. **层级差一步**：本体给垂直两轴 0.125/512 的层差，描边原来只比自己核心低 0.0625，所以高的一侧那条 4px 描边会盖住另一段核心。现在统一下沉 **0.1875**（= 0.125 层差 + 0.0625 藏自身核心），于是**任何转角上描边都同时低于两条核心**，原版 L 形完整保留，描边从底下穿过去；
      2. **两条描边自己填角**：两段都画满整步，转角处两条 4px 带自然重叠，把核心没占的那一格补上；肘部对角外侧那格仍然空着（作者要的留空）。同层转角（E-S / W-N）两带重叠色相同，重叠不可见；
      3. **每段都是 1:1 采样**：没有任何缩放 → 描边花纹密度与本体线条完全一致。
      副产物：交叉处的观感**更接近本体**——描边沉到其它连线核心之下后，本体线条不再被染料描边吃掉最外侧 1px。代码同时简化：删掉 `CORNER_FILL`、`isCorner`、`planar` 与 `createcc$underlay` 的 `lengthScale` 参数。

#### P1-3　修复预览光束在拐角处的渲染（截图二）

- **目标**：路径预览的绿色光束在转角、交汇、短段三种场景下都没有缺口与台阶
- **现状依据**：`BatchPreviewRenderer` 把折线按共线合并成「跑段」，每段提交一个世界对齐长方体；转角靠两端各延长 `HALF_BEAM`（半个束宽）重叠补角，路径首尾各延长 `GAUGE_REACH`；`WorldAlignedBeamOutline` 负责统一法线方向，避免垂直段偏暗。截图里垂直段末端在交汇处出现台阶状缺口与端点参差——说明「两段各自为盒 + 半宽重叠」这套补角在短段与交汇处并不能总是落齐
- **参考 Create 本体（已核对源码）**：上游标注世界几何只有 `Outliner.showAABB / showLine` 一条路子（`FactoryPanelConnectionHandler` 用它画起手框、`SchematicAndQuillHandler` 用它画选区），**没有"补角"先例可抄**；反而可以对照本项目自己的预览光束做法——两端各延长半个束宽做重叠——把同一套「重叠补角」思想做得更彻底。
- **建议实现**：
      a) 先按三类场景复现并记录（转角、十字交汇、相邻转角只隔一个半格步进的短段）
      b) 补角从「两端各延长半宽」改为**按转角生成立方体**或**整段延长**，保证任意段长都填满
      c) 可选：预览按目标染料着色（当前固定 `0x95CD41`，不体现将要应用的颜色）
      d) 复核长路径与大工厂下的开销（目前每个客户端 tick 重建全部光束并逐段提交 Outliner 条目）
- **验收**：三类场景截图无缺口；10 个以上仪表的路径下无闪烁、帧率无可感下降
- **实现结果（已完成，0.5.0-dev）**：查清真实成因后否掉了原来的两个候选方案。`BatchPreviewRenderer` 里两段光束在转角处**共享顶面、重叠半个束宽**，叠加渲染后必然出现一块更深的方块；同时外侧还留缺口——所以既不是"缺口"也不是"短段没落齐"，而是"重叠处双重混合 + 外侧未补"并存。
      改法：跑段改为**首尾精确相接**（内部接点不再延长，只有路径首尾仍以 `GAUGE_REACH` 探入仪表），并在每个直角接点补一块**恰好填补外侧象限**的 `cornerBox`——沿来向偏半束宽、沿去向跨越整条束宽，与两段光束**相接而不重叠**。这样既没有双重混合，也没有缺口，且与段长无关。
      预览颜色**保持绿色** `0x95CD41`：Create 的预览一贯用绿色表示"可执行"，颜色信息改由 P1-6 的 action bar 文字承担（同样的取舍见 `SchematicAndQuillHandler` 用文字报尺寸）。
- **追加实现（作者反馈后，0.5.0-dev）**：
      1. **光束减半变细**：`BEAM_WIDTH` 由 0.125（2px）改为 **0.0625（1px）**；补角块、截面半径等全部由该常量推导，自动跟随。
      2. **十字交汇处彻底不再重叠**：转角相接只解决了"接点"，而链自身（或链内两条连线）**互相交叉**时两段光束仍会占用同一空间，重叠处双重混合并因共面面片产生深度抖动，表现为十字处的深色台阶。现在改为**统一收集 + 稳定排序 + 逐块裁剪**：所有光束块按稳定 key 排序后依次提交，每块都裁掉"已被先前块画过"的部分（`drawWithoutOverlap`／`uncovered`）。裁剪只在**邻居完全覆盖该块横截面**时进行（交叉、同路重叠都满足），所以不会裁出缺口；被裁掉的部分恰好是邻居会涂的同一颜色体积，因此接缝不可见。
      排序是必需的：`previewPath` 是 `HashSet`，迭代顺序不稳定，否则交叉处"谁盖谁"会逐 tick 翻转、产生闪烁。
      3. **仪表处转弯不再显示成"十字"（第三次反馈）**：每个连线光束在仪表端会沿自身方向多伸 `GAUGE_REACH = 0.25` 格，于是**路径在仪表处转弯**时，两条连线的多余段朝相反方向各伸出一截——四条臂，看起来就是个"+"。把 `GAUGE_REACH` 由 0.25 降为 `HALF_BEAM`：光束变成"在仪表内互相重叠半个束宽"，与补角块同一套重叠量，仪表内不会留缺口，外侧也不再伸出多余的臂，转角恢复为干净的肘形。（`GAUGE_REACH` 与 `HALF_BEAM` 一致后，仪表处的接合由先画的那条光束自身的横截面覆盖，等价于补角块的作用。）
- [x] 复现三类场景并留存截图（截图一/截图二由作者提供，成因已定位到代码行）
- [x] 改补角逻辑并通过验收（编译通过 + 实机加载无异常；作者 2026-09-24 实机确认：仪表处转弯已无"十字"、1px 光束与整体观感通过）

#### P1-4　染色时复用原版的使用动作

- **目标**：染色时播放原版「使用物品」反馈（挥臂 / 使用动画），手感与其它 Create 交互一致
- **现状依据**：`DyeInteractionHandler` 命中连线时只调用 `event.setCanceled(true)`，**没有设置取消结果**，因此客户端不会播放原版使用反馈。Create 自身处理同类自定义右键的写法是 `event.setCancellationResult(InteractionResult.SUCCESS)`（见 `EdgeInteractionHandler`、`LinkHandler`、`ValueSettingsInputHandler`），个别场景再补一次 `player.swing(event.getHand())`（见 `ChainConveyorConnectionHandler`）
- **建议实现**：在「命中连线」「shift+右键进入路径模式」「右键确认整条路径」三处把取消结果设为 `SUCCESS`（按需补 `swing`），同时保留阻止打开仪表面板与放置方块的逻辑；客户端与服务器两侧保持一致，避免判定分叉
- **待定取舍**：是否改用原版染色音效 `SoundEvents.DYE_USE`（羊染色用的那个），还是保留现在 Create 的连线音效（受 `dyeEffects` 控制）
- **验收**：三种手势都有原版挥臂反馈；面板不会被误开、方块不会被误放；服务端不出现重复处理
- **实现结果（已完成）**：`DyeInteractionHandler` 的三处接管（确认整条路径 / shift 进入路径模式 / 命中单条连线）都补上了 `event.setCancellationResult(InteractionResult.SUCCESS)`，类注释同步说明了原因。`SUCCESS` 属于 `consumesAction()`，客户端的 `startUseItem` 会自行播放挥臂与使用动画，因此无需手动 `swing`。实机运行 12 次染色点击无异常；挥臂观感请在游戏里确认一眼

      术语不靠猜，全部锚定官方译文：先从 Create 6.0.10 发布 jar 里抽出 `assets/create/lang/*.json`，逐语言比对同一批键，得到"工厂仪表 / 连线 / 染料"的官方说法，再据此统一用词——
      1. **仪表**取 Create 本体的**方块名**或本体自己在正文里用的短称：de `Fabrikanzeige`、fr `jauge`（方块名 `Jauge d'usine`）、ja `ゲージ`、ko `게이지`、pt_br `medidor`（本体正文用 `Medidor de Fábrica`；方块名是 `Controlador de Estoque`，过长且语义偏"库存控制器"，HUD 不采用）、ru `контроллер`（方块名 `Фабричный контроллер`）、es_es `medidor`（方块名 `Medidor Industrial`）
      2. **连线**取本体同类方块名的用词：fr `liaison`（`Liaison d'affichage`）、ja `リンク`、ko `링크`、pt_br `conexão`（`Conexão de Redstone`）、es_es `enlace`、de `Verbindung`、ru `связь`
      3. **染料**与**颜色名**不自己译：代码里注入的是原版键 `item.minecraft.*_dye` / `color.minecraft.*`，各语言自动取原版译文
      两处特意规避了"占位参数不可变形"的语法坑：
      - **颜色词不能变格/变位**：德语与俄语的形容词要跟名词一致（`Hellgrün` → `hellgrüne Verbindungen`、`Лаймовый` → `Лаймовые связи`），而 `%2$s` 是游戏注入的固定字符串、无法改写，因此这两门语言的汇总句把颜色放进括号当作标签（`%1$s Verbindungen (%2$s) an %3$s Fabrikanzeigen`），法/西/葡/日/韩可自然前置，仍按语序翻译
      - **俄语数词变格**：`1 связь / 2 связи / 5 связей` 依赖数字，lang 文件没有复数机制，因此俄语用 `Всего связей: %1$s` 与 `связи: %3$s` 这类**标签式**结构，任何数字都成立；状态计数同理用 `%s в работе / %s в простое / %s выполнено / %s с ошибкой` 这些与数词无关的形式
      另核对：本模组复用 Create 的 `create.factory_panel.some_links_unloaded` 在 7 门语言里都存在，无需自行补译。
- **校验方式（可复用）**：`verifylang.ps1` 脚本对比 9 个文件的键集合与占位符集合（`%1$s/%2$s/%3$s/%s`）是否与 `en_us` 完全一致，并检查重复键。结果：9 个文件各 22 键、键位一致、占位符一致、无重复键、JSON 全部可解析。

      已核对的细节（避免以后踩坑）：`Builder.define(...)` 结尾会 `context = new BuilderContext()`，所以翻译键**不会串到下一个选项**；`push`/`build` 会 `context.ensureEmpty()`，若键没被消费会抛 `IllegalStateException`，因此 `.translation()` 必须紧贴对应的 `define`/`push`。
      附带说明：Configured 自身只带 de/en/es/it/ru 五种语言，所以法语/日语/韩语/葡语的配置界面按钮（Save/Reset 等）会回落成英文，这是 Configured 的限制、不是我们的残留。
      证据（均来自反编译/源码，非推测）：`NeoForgeValue.getTranslationKey()` 返回 NeoForge `ValueSpec.getTranslationKey()`，而它只有在配置构建时显式调用 `Builder.translation("...")` 才会被赋值，默认 **null**；Configured 的三处显示逻辑都以它为准——
      1. 选项名：`ConfigScreen$ConfigItem` 里 `if (getTranslationKey() != null && I18n.exists(key)) return Component.translatable(key)`，否则回退 `getName()`（即路径末段，如 `dyeConsumption`）；
      2. 注释：`NeoForgeValue.getComment()` 查 `I18n.exists(key + ".tooltip")`（字节码里的拼接常量就是 `\u0001.tooltip`），查到用译文，查不到回退代码里的英文 `comment(...)`；
      3. 分组标题：`NeoForgeFolderEntry.getTranslationKey()` 取 `spec.getLevelTranslationKey(path)`，同样先 `I18n.exists` 再回退 `getEntryName()`。
      改之前这三处全都走回退分支，所以界面才会是英文原文加原始键名。
- [x] 修掉操作栏提示溢出（作者逐语言实测：fr / pt / es / ru / de 超宽，en 勉强，ja / ko / zh 通过）：
      **原版操作栏不可能换行**，这点已核对源码（`build/moddev/artifacts/neoforge-21.1.248-sources.jar` 里的 `net.minecraft.client.gui.Gui`）：`setOverlayMessage` 只存一个 `Component` 与 60 tick 计时；`renderOverlayMessage` 用 `font.width(component)` 量一次宽，再 `drawStringWithBackdrop(font, component, -k/2, -4, k, color)` 画**一行**——`\n` 不会被当作换行（且会让背景板的宽度算错 k），所以位置固定居中、既不换行也不避让屏幕边缘。要"两行"只能自己画 HUD。
      定稿（作者决定："那就直接显示如图：右键确认 · 右键空白处取消"）：**该行只留两个手势**，去掉连线/仪表计数与手中染料名。**作者实测：通过。**
      1. 理由：计数与染料名是整行最长、而选路过程中信息量最低的部分——染料就在玩家手上，链的规模由不断延伸的预览光束与末尾那个闪烁框已经能看出来；手势才是选路当中真正需要读的；

      3. 结果宽度（按 6px/字符、中日韩全角按 9px 估算）：de 348px / fr 348 / ru 294 / es 282 / pt 276 / en 252 / ja 162 / ko 126 / zh 117。
      对照基准：修前的 en≈546px 就已经"勉强容纳"，现在最宽的语言只有它的约 64%，任何语言都不再依赖屏幕够宽，将来加语言也不容易再犯。

#### P1-6　修复批量染色的交互手感

- **目标**：让「选路 → 确认 / 取消」这套交互在任何场景下都可预期，且密集仪表墙里也不容易误操作
- **现状依据（逐条来自代码，非推测）**：
      1. **三种手势都是右键，语义只靠 shift 区分**：shift+右键仪表 = 开始/追加（`DyeInteractionHandler.handlePathClick`），非 shift 右键**末尾仪表** = 确认（`resolvePendingClick`），非 shift 右键**其它任何位置** = 取消。想追加却漏按 shift 就变成确认或取消，想确认却带着 shift 就变成追加/撤销。
      2. **没有任何键位绑定**：整个模组没有 keybind，取消只能"右键空白处"；仪表墙常紧贴方块，找不到空白就只能等超时（`BatchDyeSelection.TIMEOUT_MS = 60_000`，60 秒无操作自动清除，且**清除时没有任何提示**）。
      3. **只能按顺序从末尾回退**：`step()` 只在"再次扫到末尾仪表"时弹出一个节点；链中间某个节点扫错了只能整条重来。
      4. **链由准星扫过自动增长**：`onClientTick` 用 hover 变化驱动追加，密集墙里很容易多挂/漏挂；漏掉要靠 shift+右键点击补，而 shift+右键落在末尾节点上又是"撤销"，语义冲突。
      5. **确认前看不到规模与颜色**：预览只有绿色光束，没有"将染 N 条连线 / M 个仪表"的计数；光束颜色固定 `0x95CD41`，也不提示确认后会变成手中染料的颜色。
      6. **静默失效**：手上没有染料、切换维度、超时这几种情况都会直接 `clear()`，只有 action bar 一行字，玩家容易以为自己还在选路。
- **参考 Create 本体（已逐条核对源码，可作为设计依据）**：
      Create 自己就有一套"shift+右键起手 → 再点下一个"的连接流程（`FactoryPanelConnectionHandler`），以及一套两步选区流程（`SchematicAndQuillHandler`）。它们的共同约定是：
      1. **shift = 中止**，不是"追加"：两者的取消分支都判 `isShiftKeyDown()`（`FactoryPanelConnectionHandler.onRightClick` 尾部、`SchematicAndQuillHandler` 第 101 行）。我们目前把 shift 用作"追加"，与上游习惯相反。
      2. **提示是持续刷新的**：`FactoryPanelConnectionHandler.clientTick()` 每 tick 都 `displayClientMessage(..., true)` 显示"点击第二个面板"；空闲时用 `Component.empty()` 清空提示。
      3. **起手对象有闪烁高亮**：同一处用 `Outliner.showAABB(connectingFrom, connectingFromBox)`，颜色在两色间交替（`0x38b764` / `0xa7f070`），`lineWidth 1/16`。
      4. **确认前先告诉结果规模**：`SchematicAndQuillHandler` 在选完两点后显示 `schematicAndQuill.dimensions`（尺寸），Abort/NoTarget 也各有明确文案。
      5. **失败给具体原因 + 拒绝音效**：`checkForIssues()` 返回具体原因（已连接 / 输入已满 / 不同朝向 / 不同平面 / 太远 / 无物品），用红色显示并播 `AllSoundEvents.DENY`。
      6. **键位是替代路径而非唯一路径**：`SchematicAndQuillHandler` 额外提供 `AllKeys.ACTIVATE_TOOL`（Ctrl）确认；`AllKeys` 还把 Shift / Ctrl / Alt 本身注册成**可改键**的 modifier（`SHIFT_MODIFIER` / `CTRL_MODIFIER` / `ALT_MODIFIER`，配合 `ConflictSafeKeyMapping`），这正是 6.0.10 更新日志里 "Add keybinds for ctrl, shift and alt modifiers" 的那条。
- **建议改进（按性价比排序，方向对齐上游习惯）**：
      a) **把取消改回 shift**：shift+右键 = 中止（与 Create 一致），确认与追加交给普通右键 + 键位；这是行为变更，需写进 CHANGELOG
      b) **键位**：`确认` / `取消` / `逐步回退` 各给一个键（仿 `AllKeys` 的写法，modifier 尽量可改键），取消不再依赖"有没有空白处可点"
      c) **持续提示 + 实时规模**：选路期间每 tick 刷新 action bar，显示"点击下一个仪表 / 将染 N 条连线 / M 个仪表 + 目标颜色名"（仿 `clientTick` 的持续提示 + `schematicAndQuill.dimensions`）
      d) **当前末尾闪烁高亮**：仿 `connectingFromBox`，用两色交替的 Outliner 框标出"确认目标是哪个仪表"
      e) **失败具体化**：扫到不同网络的仪表、超出距离等情况给红色原因文案 + `DENY` 音效，替代现在的静默忽略
      f) **回退与纠错**：允许从末尾连续回退（键位逐步退），再考虑 shift+右键非末尾节点 = 截断到该节点
      g) 长期可选：颜色预设面板（与 P2-2 合并），彻底摆脱"必须手持染料"的限制
- **验收**：密集墙（≥12 个仪表）下连续构建 / 纠错 3 次无误操作；在没有空白可点的贴墙场景仍能取消；~~确认前能看到将染连线数与目标颜色名~~（**该条已改：操作栏只留两个手势，计数与颜色名不再显示**，理由与宽度实测见 P1-5）
- **实现结果（已完成 a、c、d、e 与"空点击中止"，0.5.0-dev）**：
      1. **手势改为与本体一致**（`DyeInteractionHandler`）：模式内 **Shift+右键 = 中止**（不再追加）；普通右键落在**其它仪表**= 追加、落在**末尾仪表**= 确认、落在**起始仪表**= 取消（对应本体的"再点一次源面板即清除"）、落在非仪表= 取消。起始仪表同时是 size=1 时的末尾，因此"什么都没链就确认"自然退化为取消。
      2. **空点击也能中止**（新增 `PathDyeInputHandler`）：本体是在输入层拦 `InputEvent.InteractionKeyMappingTriggered` 才做到"右键空气也中止"，本项目原先依赖方块交互事件，点空气根本进不来；现在按同样做法补上，贴墙没空白也能取消。
      3. **持续提示 + 实时规模**（新增 `PathDyeOverlay`）：每 tick 刷新 action bar，显示「将染 N 条连线 / M 个仪表 · <手中染料名>」，并把两种确认/取消手势写在提示里——对应本体的 `clientTick()` 一直挂着 "click second panel"。
      4. **确认目标闪烁高亮**：用 `Outliner.showAABB` 把**末尾仪表**按本体那套两色交替（`0x38B764` / `0xA7F070`，`lineWidth 1/16`）框住，框的几何照 `FactoryPanelConnectionHandler.getBB` 的公式算（槽位中心 + 沿平面两轴各 3/16，贴墙不鼓出）。
      5. **失败具体化 + 拒绝音效**：扫到不连通/已在链上的仪表时，**显式点击**会给出红色原因（`path_no_route` / `path_already_in_chain`）并播放 `AllSoundEvents.DENY`；准星扫过时的拒绝**故意保持静默**——密集墙里扫过几十个无关仪表，逐个报错只会变成噪音（这是与本体"点击式"流程的必要差异）。
      6. **静默失效改为明确提示**：超时（新增 `path_timeout`）、手中失去染料（新增 `path_no_dye`）、离开世界各给一行提示，不再无声清除。
      新增语言键 5 个（en_us / zh_cn 同步）。
- **追加实现（作者反馈后，0.5.0-dev）**：
      1. **修掉"确认时弹出本体的面板界面"**（真实缺陷）：`BatchDyeSelection.holdingDye` 接受**任意一只手**的染料，但 `DyeInteractionHandler.onRightClickBlock` 第一行就用「本次交互手拿的是不是染料」做闸门。于是染料放在**副手**时，链仍然有效，而确认点击会直接漏给本体——本体照常打开仪表配置界面，路径染色失败。现在**待确认链会接管所有右键**（不论手持什么），染料取值改为"主手优先、否则副手"；两手都没有染料时清除链并提示原因。这同时解释了为什么"最后一步"总是失败。
      2. **选路期间屏蔽本体的仪表悬浮提示**（新增 `client/ValueSettingsClientMixin`）：`FilteringRenderer.renderOnBlock` 在准星落到仪表上时会把 `getTip()`/`getAmountTip()` 交给 `CreateClient.VALUE_SETTINGS_HANDLER.showHoverTip(...)`，显示"单击以配置 / 按住以改变目标数量"——所示即截图里那几行字。这既是本链**故意屏蔽**的动作，又正好压在待确认的仪表上，所以在 `showHoverTip` 头部按 `BatchDyeSelection.hasSelection()` 取消（本模组自己的 action bar 提示与末尾闪烁框保留）。
- [x] 键位（确认 / 取消 / 逐步回退）：**本期不加**（作者决定）。记录备查：本体也没有为连接流程提供键位（起手在面板 GUI 里、取消靠输入层），若将来要做，按 `AllKeys` 的写法并可考虑 modifier 可改键
- [ ] 作者在游戏内确认观感与手感（尤其：Shift 语义变更是否符合你的预期；密集墙里提示是否过于频繁；1px 光束是否够细）
